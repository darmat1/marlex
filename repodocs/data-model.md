## Область и источник истины
- Персистентные данные существуют в двух независимых местах сегодня: (1) Postgres через Drizzle (`server/src/db/schema.ts`) — таблицы `user`/`session`/`account`/`verification` (better-auth) и `client_profiles`/`projects`; (2) клиентское состояние в localStorage через zustand `persist` (`src/lib/store/useMarlexStore.ts`) — модель `MarlexProject` (`src/types/index.ts:28`) плюс отдельное поле стора `currentResult: GenerationResult` (`src/types/index.ts:124`, слайды/промпты/экспортированные тексты) и BYOK-ключи провайдеров.
- Источник истины по схеме — `server/src/db/schema.ts`, импортируемый (не копируемый) во все места, где схема нужна (см. [[decisions#ADR-002]]). Сегодня `api/index.ts` держит собственную разошедшуюся копию — это активная находка, не целевое состояние.
- Клиентская модель (`MarlexProject`) и серверная модель (`projects`) сегодня не пересекаются ни одним доменным полем — общие есть только служебные `id`/`createdAt`/`updatedAt`, ни одно смысловое поле (контент, статус, привязки) не совпадает — целевое состояние требует явного решения, синхронизировать их или сознательно оставить раздельными (см. [[legacy_warning]]).

## Модель и контракты
- `user` / `session` / `account` / `verification` — стандартные таблицы better-auth.
- `client_profiles` — профили клиентов эксперта/фаундера (владелец функциональности студии).
- `projects` — карусели/проекты; `userId` — nullable FK на `user.id` (`onDelete: 'cascade'` в актуальной схеме), предназначен для ownership-scoping, но не используется маршрутами сегодня (см. [[decisions#ADR-003]]).
- `MarlexProject` (клиент, `src/types/index.ts:28`) — метаданные проекта (id/название/бренд-хендл/цвета/шрифт/участники/таймстемпы). Сырые слайды, промпты и экспортированные тексты для Telegram/LinkedIn/Threads живут отдельно, в поле стора `currentResult: GenerationResult` (`src/types/index.ts:124`) — весь стор персистится целиком в localStorage без `partialize`.

## Инварианты и семантика хранения
- `projects.userId` должен заполняться из аутентифицированной сессии при создании — не приниматься из тела запроса (см. [[decisions#ADR-003]]).
- Идемпотентность записи: `POST /api/projects` сегодня всегда делает `INSERT` — повторный вызов с тем же `id` должен обновлять запись (upsert), не падать на конфликте первичного ключа (см. [[migration_backlog#MB-013]]).

## Владение чтением и записью
- Только `api/index.ts` (после [[decisions#ADR-002]]) читает/пишет Postgres напрямую; рендерер (`src/`) обращается к данным только через HTTP.
- `server/src/index.ts` — не источник правды для схемы/auth, только локальный dev-сервер поверх общего кода.
- Клиентское состояние (`useMarlexStore`) — единственный владелец localStorage-персистентности; BYOK-ключи требуют `partialize`, исключающего их из открытого хранения (см. [[security]]).

## Эволюция, совместимость и восстановление
- Каталога drizzle-миграций сегодня нет, хотя `drizzle.config.ts` настроен — целевое состояние: первая миграция генерируется и коммитится, дальнейшие изменения схемы идут через миграции, не ручной ALTER (см. [[migration_backlog#MB-013]]).
- Откат/бэкап Postgres — вне зоны ответственности приложения (управляется хостингом БД); приложение не реализует собственный backup-механизм.
- Локальные данные (localStorage) — не версионируются; при смене формы `MarlexProject` учитывать миграцию/совместимость с уже сохранёнными у пользователей данными (риск при следующих изменениях модели).
